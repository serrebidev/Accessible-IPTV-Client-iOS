# Video AirPlay without AVPlayer — iOS AirPlay architecture research

Scope: iOS 17+ (with notes on iOS 26 / "OS 27" where relevant). Question: can a third-party iOS app that renders video itself (libVLC / VLCKit 4 into a UIView, audio via its own AudioUnit on an AVAudioSession with category `.playback` / mode `.moviePlayback`) send VIDEO — not just audio — to an AirPlay / AirPlay 2 receiver without using AVPlayer? Sources are Apple documentation, WWDC transcripts, Apple Developer Forums, and maintainer statements in open-source player projects. macOS-only behaviour is flagged where it appears; nothing here is generalized from Android/Windows.

Bottom line up front: On iOS, AirPlay *video* (the "receiver plays the content itself" mode, as opposed to screen mirroring) is only exposed through AVFoundation's player objects (AVPlayer/AVQueuePlayer with an AVPlayerItem backed by a URL-reachable asset). There is no public iOS API that hands an arbitrary, already-decoded video stream to AirPlay. The only non-AVPlayer "enhanced buffering" path Apple documents is audio-only (AVSampleBufferAudioRenderer). An app that renders via libVLC gets, at most, AirPlay *audio* routing via AVAudioSession, plus full-screen mirroring via Control Center. This is a documented-API absence corroborated by developer-reported behaviour; see per-question sections for what is (a) documented, (b) developer-reported, and (c) inferred.

## Q1: What does AVRoutePickerView do for an app with no AVPlayer? Is it inert? Audio-only?

### Takeaway
AVRoutePickerView is a *route picker UI*, not a video pipeline. It is not inert without an AVPlayer — it still lists nearby receivers and, because the app's AVAudioSession (category `.playback`) is AirPlay-eligible, selecting a receiver routes the app's *audio* to it. But it has no mechanism to carry video except through an AVPlayer: the class literally exposes a `player: AVPlayer?` property ("The player object to perform routing operations for"). With no AVPlayer, nothing video-shaped exists for the system to hand to the receiver, so video stays on-device.

### Cited findings
- AVRoutePickerView "represents a button that users tap to stream audio/video content to a media receiver… When the user taps the button, the system presents a popover that displays all of the nearby AirPlay devices that can receive and play back media. If your app prefers video content, the system displays video-capable devices higher in the list." It documents a property `var player: AVPlayer?` — "The player object to perform routing operations for." — [AVRoutePickerView | Apple Developer Documentation](https://developer.apple.com/documentation/avkit/avroutepickerview) (Apple reference documentation, page © 2026, class available iOS 11+; retrieved 2026)
- WWDC19 Session 501 (Apple, AVKit/Connected Media engineers): "To add an AirPlay picker, use AVRoutePickerView… All I have to do is create a AVRoutePickerView and add it to my view hierarchy. And in iOS 13, I can set prioritizesVideoDevices to true and that will give me a route button icon that is focused on video… and it also sorts those TV destinations to the top." The session's entire video-AirPlay model is built around AVPlayer/AVQueuePlayer/AVPlayerViewController. — [Reaching the Big Screen with AirPlay 2 — WWDC19 Session 501 transcript](https://developer.apple.com/videos/play/wwdc2019/501/) (June 2019; Apple primary source, older than 2023 but it is the canonical Apple statement of the in-app AirPlay video architecture and nothing newer contradicts it)
- Apple's current "Supporting AirPlay in your app" article describes the picker purely as route UI ("The picker provides users with a list of potential AirPlay devices") and describes audio routing as an AVAudioSession concern: "set your audio session's route-sharing policy to `.longForm`… This setting identifies the audio that an app plays." — [Supporting AirPlay in your app | Apple Developer Documentation](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app) (Apple reference documentation, page © 2026; retrieved 2026)
- Developer-reported: with a non-AVPlayer renderer (media_kit/mpv, same architecture as libVLC), "When casting a video to AirPlay, only the audio is sent while the video remains on the device. I'm assuming this is because media_kit renders the actual image of the video on its own instead of using Apple's AVPlayer class?" — [media-kit issue #207, calebvetter](https://github.com/media-kit/media-kit/issues/207) (May 24, 2023)
- Developer-reported (audio-only routing via AVAudioSession is real and independent of video): expo-audio issue — "This keeps the local AVPlayer in control of playback while still routing audio to the AirPlay device via AVAudioSession." — [expo/expo#48342](https://github.com/expo/expo/issues/48342) (2025-era issue; retrieved 2026)

### Inferences
- (c) For the concrete libVLC app: adding AVRoutePickerView will present receivers and will route the app's AudioUnit output (`.playback`/`.moviePlayback` session) to a selected AirPlay receiver as audio-only. The UIView rendered by libVLC will not be transmitted. The picker is therefore not "inert", but it is audio-only in effect for this app.
- (c) `prioritizesVideoDevices = true` only changes sort order/iconography; it does not create a video path.

### Gaps
- I found no Apple document that states in one sentence "AVRoutePickerView without AVPlayer routes audio only"; this is assembled from the picker's documented API surface (a) plus consistent developer reports (b). No counterexample (video working without AVPlayer) was found anywhere.

## Q2: What is required for AirPlay video — AVPlayer/AVPlayerItem, allowsExternalPlayback, usesExternalPlaybackWhileExternalScreenIsActive? Does the receiver fetch the URL itself?

### Takeaway
AirPlay video is a property of AVPlayer: `allowsExternalPlayback` (default true) permits the player to switch to "external playback mode", which is Apple's term for AirPlay video and wired HDMI/VGA output. The content is modeled as an AVPlayerItem whose AVAsset is created from a URL; Apple's own enhanced-buffering guide creates the asset with `AVAsset(url:)` from "a URL that points to local or cloud content". Whether the receiver re-fetches the URL over the network is not stated verbatim in the docs I could retrieve, but the entire model (URL-based asset handed to the system; HLS authoring requirements imposed on *your playlist* because the TV plays it; "the player can transition smoothly between variants") only makes sense if the receiver becomes the player of a network-reachable stream.

### Cited findings
- `allowsExternalPlayback`: "A Boolean value that indicates whether the player allows switching to external playback mode… The default value of this property is true." (iOS 6.0+). — [allowsExternalPlayback | Apple Developer Documentation](https://developer.apple.com/documentation/avfoundation/avplayer/allowsexternalplayback) (Apple reference documentation, page © 2026; retrieved 2026)
- `usesExternalPlaybackWhileExternalScreenIsActive`: "A Boolean value that indicates whether the player should automatically switch to external playback mode while the external screen mode is active… The default value of this property is false. The value of this property has no effect if allowsExternalPlayback is false." — [usesExternalPlaybackWhileExternalScreenIsActive | Apple Developer Documentation](https://developer.apple.com/documentation/avfoundation/avplayer/usesexternalplaybackwhileexternalscreenisactive) (Apple reference documentation, page © 2026; retrieved 2026)
- "External playback mode is when video data is sent to an external device such as Apple TV via AirPlay and the mini-connector-based HDMI/VGA adapters for full screen playback at its original fidelity. AirPlay Video playback is also considered as an 'external playback' mode." — [Stack Overflow #21763975, answer citing Apple's AVPlayer docs](https://stackoverflow.com/questions/21763975/uievents-sent-from-apple-tv-while-using-avplayer-external-playback-mode) (2014; old, but it quotes Apple's own definition which is unchanged in current docs)
- Apple's "simple enhanced buffering" guide (the canonical "make AirPlay 2 fast" path): "The AVPlayer and AVQueuePlayer classes provide the simplest way to enhance buffering for your content with AirPlay 2… Identify a URL that points to local or cloud content that you want to play. Create an AVAsset instance with a URL, and then create an AVPlayerItem instance with that asset." — [Implementing simple enhanced buffering for your content | Apple Developer Documentation](https://developer.apple.com/documentation/avfoundation/implementing-simple-enhanced-buffering-for-your-content) (Apple reference documentation, page © 2026; retrieved 2026)
- WWDC19/507 (HLS team): AirPlay 2 TVs impose authoring requirements on *your HLS playlist* — "These TVs will stick with the codec they start with", "do not switch between HEVC and H.264", "use WebVTT for subtitles", FairPlay "10% partial encryption… other patterns will not work" — i.e. the TV is the entity decoding/playing the stream. — [HLS Authoring for AirPlay 2 Video — WWDC19 Session 507 transcript](https://developer.apple.com/videos/play/wwdc2019/507/) (June 2019; Apple primary source)
- WWDC19/501: "Remember at any time, a user could take that video and want to send it and AirPlay it to a TV. So it's important that you have a full range of variants in your playlist that are appropriate for a TV, including variants that support 4K, HDR and surround sound… This makes sure that your video is fully supported on any device it plays back on and it also makes sure that the player can transition smoothly between variants using the same video codec." Also: use AVQueuePlayer or reuse one AVPlayer when AirPlaying, "because when AirPlaying, the system doesn't know that a new piece of video is going to be arriving." — [WWDC19 Session 501 transcript](https://developer.apple.com/videos/play/wwdc2019/501/) (June 2019; Apple primary source)
- Developer-reported corroboration that the receiver takes over the *source*: media_kit maintainer alexmercerind — "Chromecast, AirPlay etc. take a complete media source & just stream it themselves. It has nothing to do with video rendering, playback, decoding etc." — [media-kit issue #207](https://github.com/media-kit/media-kit/issues/207) (July 1, 2023)
- Developer-reported: setting `allowsExternalPlayback = false` yields audio-only AirPlay ("if enabled allowsExternalPlayback = false then only video plays as an audio") — [Stack Overflow #72316638](https://stackoverflow.com/questions/72316638/avplayerviewcontroller-plays-audio-through-airplay-when-allowsexternalplayback-i) (2022; borderline age, included as behaviour report, not as API authority)

### Inferences
- (c) For the concrete IPTV case: because AirPlay video means the *receiver* plays a URL-modeled asset, the receiver must be able to reach the stream. A live MPEG-TS URL that is locked to the iOS device's IP/session ("only that device may connect") would very likely fail to play on the receiver even if the app used AVPlayer — the Apple TV would be a different network client. This is inference from the URL-asset model and the receiver-plays-it evidence above, not a sentence Apple publishes.
- (c) `usesExternalPlaybackWhileExternalScreenIsActive` is only about the interplay between AirPlay video and *mirroring* (external screen mode); irrelevant to an app with no AVPlayer.

### Gaps
- No current Apple page retrieved that states verbatim "the AirPlay receiver fetches the URL itself". The WWDC19 sessions and the URL-asset API are strong circumstantial evidence; the media_kit maintainer statement is the clearest plain-language confirmation, and it is developer-reported, not Apple documentation.

## Q3: Is there any public API to hand an arbitrary already-decoded video stream to AirPlay (AVSampleBufferDisplayLayer, AVPlayerLayer, AVDisplayManager, AVRouting, AVOutputContext)?

### Takeaway
No. AVSampleBufferDisplayLayer's entire documented surface is local rendering (plus capture protection and backgrounding); it has no external-playback/AirPlay API. AVPlayerLayer is bound to an AVPlayer. AVDisplayManager (tvOS) is about display modes, not routing. AVRouting is for adding *custom protocols* to the picker (see Q4). AVOutputContext (macOS-only for route control) does not exist as an iOS video-feed API. Apple's only documented "bring your own samples" AirPlay path is audio-only: AVSampleBufferAudioRenderer + AVSampleBufferRenderSynchronizer ("flexible enhanced buffering").

### Cited findings
- AVSampleBufferDisplayLayer: "An object that displays compressed or uncompressed video frames." Full topic list: sampleBufferRenderer, isReadyForDisplay, controlTimebase, videoGravity, preventsCapture, isOutputObscuredDueToInsufficientExternalProtection, preventsDisplaySleepDuringVideoPlayback, preventsAutomaticBackgroundingDuringVideoPlayback, decode-failure notifications. No AirPlay/external-playback member exists. — [AVSampleBufferDisplayLayer | Apple Developer Documentation (mirror of current docs)](https://github.com/livingston/apple-docs/blob/main/documentation/AVFoundation/AVSampleBufferDisplayLayer.md) (mirror of Apple reference documentation, © 2026; retrieved 2026)
- Apple's "flexible enhanced buffering" — the non-AVPlayer enhanced-buffering option — uses only AVSampleBufferAudioRenderer and AVSampleBufferRenderSynchronizer (audio renderer + timeline). It "stream[s] content faster to AirPlay-enabled devices and supported CarPlay vehicles" but enqueues *audio* sample buffers only. — [Implementing flexible enhanced buffering for your content | Apple Developer Documentation](https://developer.apple.com/documentation/avfoundation/implementing-flexible-enhanced-buffering-for-your-content) (Apple reference documentation, page © 2026; retrieved 2026)
- Apple's AirPlay adoption article lists exactly two playback API sets for AirPlay enhanced buffering: "For simple enhanced buffering, use AVPlayer or AVQueuePlayer. This works well for video content. For more flexibility… use AVSampleBufferAudioRenderer and AVSampleBufferRenderSynchronizer. This option is better for apps that require control over I/O, perform preprocessing on their media data, or have a DRM model that AVPlayer doesn't support." — [Supporting AirPlay in your app | Apple Developer Documentation](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app) (Apple reference documentation, page © 2026; retrieved 2026)
- Developer-reported, exact-match question: "Is it possible render video frames directly to AirPlay from an iOS app… Similarly to how I am able to render those frames directly to an AVSampleBufferDisplayLayer on the iOS device. I know that I can use AirPlay with the HTTP Live Streaming (HLS) protocol, but… the video is being generated on the actual iOS device and thus, I want to stream it in 'real time' to AirPlay." — [Stack Overflow #76450826](https://stackoverflow.com/questions/76450826/is-it-possible-render-video-frames-directly-to-airplay-from-an-ios-app) (June 2023; the question itself is evidence of the API gap; no accepted solution exists — page fetch failed twice with 504, so answer content is unverified; see Gaps)
- Developer-reported, same conclusion from a maintainer who investigated: birros (media_kit member): "Well, after reflection, it seems impossible in the near future. As a proof, even IINA can't implement it for 6 years!!! See: iina/iina#63" (IINA is macOS/mpv — flagged as macOS evidence; the iOS-side media_kit conclusion stands on its own). — [media-kit issue #207](https://github.com/media-kit/media-kit/issues/207) (May 24, 2023)
- Apple Developer Forums, exact-match question with zero replies: "we are trying to create an app that has to be able to send an arbitrary video url (https, mp4) to airplay rather than using the native movie player (AVPlayer). So far we haven't found an example or developer that has attempted to do this." — [Apple Developer Forums thread 116772](https://developer.apple.com/forums/thread/116772) (2017; old, and the forum page is behind a bot check so only the search snippet was retrievable — noted as weak, historical evidence of the same gap)

### Inferences
- (c) The absence of any video-sample-buffer-to-AirPlay API across AVFoundation's current documentation, combined with Apple's own framing that the *flexible* (non-AVPlayer) path exists for "apps that require control over I/O [or] perform preprocessing" yet is audio-only, strongly implies Apple deliberately does not expose decoded-video upload to AirPlay on iOS. The only frame-accurate video the system will send is what an AVPlayerItem decodes from its asset.
- (c) The "alternate way to stream pre-rendered frames" hypothesized by the media_kit reporter (the flexible-enhanced-buffering doc) does not actually carry video — reading the doc shows audio renderers only. His hope was misplaced.

### Gaps
- Could not retrieve the answers (if any) on SO #76450826 (504s); the question standing unanswered since June 2023 is itself weak corroboration.
- AVOutputContext on iOS: I did not find an iOS-facing AVOutputContext video API; macOS has AVOutputContext for route picking (per the macOS-focused gist in search results — macOS-only, not relied on for iOS claims). No iOS documentation page for AVOutputContext route control was located; treated as "no evidence it helps on iOS" rather than "proven absent".

## Q4: What is the AVRouting framework, which iOS version, and does it apply to AirPlay video or only custom protocols?

### Takeaway
AVRouting (iOS 16.0+) lets a third-party app add *its own non-AirPlay protocol/devices* as rows in the system route picker, via a Media Device Discovery Extension and AVCustomRoutingController. It does not change what can be sent over AirPlay, and it does not give an app a way to push decoded video to anything — it is a discovery/selection mechanism for custom protocols, plus playback arbitration (AVRoutingPlaybackArbiter). A brand-new AVSystemRouting framework (iOS/iPadOS 27.0) generalizes this with "media device extensions" provided by protocol vendors; it is explicitly about routing/launching URL playback on third-party receivers, still not about feeding frames to AirPlay.

### Cited findings
- "Use the AVRouting framework to add third-party devices and protocols to AVRoutePickerView. This enables a user to stream AV content through a third-party protocol using the same system menu as AirPlay… If your app's bundle includes an extension with the Media Device Discovery Extension entitlement, the system runs the extension and adds its associated third-party protocol to the picker, if the device resides nearby." Platforms: iOS 16.0+, iPadOS 16.0+, Mac Catalyst 16.0+, macOS 13.0+, tvOS 26.0+. Topics: AVCustomRoutingController, AVCustomRoutingControllerDelegate, AVCustomRoutingEvent, AVCustomRoutingActionItem; Playback arbitration: AVRoutingPlaybackArbiter, AVRoutingPlaybackParticipant. — [AVRouting | Apple Developer Documentation](https://developer.apple.com/documentation/avrouting) (Apple reference documentation, page © 2026; retrieved 2026; also mirrored at [github.com/incrediblecrab/apple-os-documentation AVRouting.md](https://github.com/incrediblecrab/apple-os-documentation/blob/main/documentation/AVRouting.md))
- AVRoutePickerView doc cross-reference: "In iOS 16 and later, you can add devices to the list that implement custom protocols." and property `customRoutingController: AVCustomRoutingController?` — "A routing controller that enables connections to non-AirPlay devices." — [AVRoutePickerView](https://developer.apple.com/documentation/avkit/avroutepickerview) / [customRoutingController](https://developers.apple.com/documentation/avkit/avroutepickerview/customroutingcontroller) (Apple reference documentation; retrieved 2026)
- AVSystemRouting (the "OS 27" successor): "Route media from a playback app to hardware supported by a media device extension." Platforms: iOS 27.0+, iPadOS 27.0+. "Use this framework to react to the selected route, launch URL playback or a companion app on the receiver, and observe remote playback… AVSystemRouteSession — Starts playback using a URL and supported launch mode." Also: "Keep AVRouting for its existing custom-route and playback-arbitration APIs; this new framework does not retroactively change their minimum availability." — [AVSystemRouting (mirror of Apple documentation, reviewed September 8, 2026)](https://github.com/incrediblecrab/apple-os-documentation/blob/main/documentation/AVSystemRouting.md) (mirror of Apple reference documentation for iOS 27; retrieved 2026 — note this is a community mirror, not apple.com; the underlying pages are developer.apple.com/documentation/avsystemrouting)

### Inferences
- (c) AVRouting is irrelevant to the concrete problem twice over: (1) it adds *custom protocols* to the picker, it does not alter AirPlay's requirements; (2) even for a custom protocol, the app would still have to implement the entire sender side of that protocol itself (the framework supplies discovery + selection UI + arbitration, not an encoder). It is not a backdoor for pushing libVLC's decoded frames to an Apple TV.
- (c) AVSystemRouting's "starts playback using a URL" session model confirms that even Apple's newest routing architecture remains URL/hand-off based, not frame-upload based.

### Gaps
- The AVSystemRouting details come from a GitHub mirror of Apple's docs (the live apple.com pages are JS-rendered and returned only titles to the fetcher). The mirror states "reviewed September 8, 2026". The existence of the framework and its iOS 27 availability is corroborated by the AVRouting mirror's "Relationship to OS 27 system routing" section, but I did not independently verify every AVSystemRouting symbol on apple.com.

## Q5: How do Control Center AirPlay / Screen Mirroring differ from in-app AirPlay, and what does each do to this app's video and audio?

### Takeaway
In-app AirPlay (AVRoutePickerView / AVPlayerViewController) is *content hand-off*: for AVPlayer-based video, the receiver plays the asset itself at full fidelity; for a non-AVPlayer app, only the audio session follows the route. Control Center "Screen Mirroring" is a system-level screen capture stream of the whole device display — it works regardless of what framework rendered the pixels, so it *will* carry a libVLC-rendered UIView (with mirroring's latency/quality characteristics), and the app cannot prevent its video from being mirrored this way. Control Center's audio route picker (without mirroring) routes audio only.

### Cited findings
- WWDC19/501 distinguishes the modes: "You can use AirPlay to wirelessly send a video to watch on your TV or listen to music… And you can also share pretty much anything from your iOS or macOS screen using AirPlay Mirroring." — [WWDC19 Session 501 transcript](https://developer.apple.com/videos/play/wwdc2019/501/) (June 2019; Apple primary source)
- Developer-reported that `allowsExternalPlayback = false` does NOT stop Control Center mirroring: "I have been trying to disable airplay for videos and setting AvPlayer.allowsExternalPlayback = NO; But it is not working for me. I am still able to go to control center and cast video to apple tv…" — [Stack Overflow #45450460](https://stackoverflow.com/questions/45450460/avplayer-allowsexternalplayback-no-is-not-working-as-expected) (2017; old but consistent with the documented mirroring/content-hand-off split)
- Apple Support–style distinction (third-party receiver vendor): "Use the app's AirPlay button for media, or Control Center's Screen Mirroring button for your display." — [1001 TVs](https://www.1001tvs.com/airplay-vs-screen-mirroring/) (SEO vendor page, undated; used only for the user-facing distinction, which matches Apple's WWDC framing)
- Reddit r/appletv practitioner summary: "screen mirroring is just casting what is displayed onto a display, whilst airplay sends the video stream directly to the display" — [reddit.com/r/appletv thread](https://www.reddit.com/r/appletv/comments/jwikpf/just_the_technology_please_screen_mirroring_vs/) (2020; community source, consistent with Apple's model; included as practitioner corroboration only)
- Apple Developer Forums AirPlay tag shows a current (iOS 26.5) thread about mirroring behaviour from iPhone to a Mac with Photos-app video — evidence that in 2026 mirroring remains the system-level path that carries arbitrary app video. — [Apple Developer Forums — AirPlay tag](https://developer.apple.com/forums/tags/airplay) (2026; only the snippet was retrievable — forum is behind a bot check)

### Inferences
- (c) For the concrete libVLC app: Control Center Screen Mirroring is the *only* zero-code way its video reaches an AirPlay receiver, because mirroring captures the compositor output (the UIView's rendered pixels) rather than the media pipeline. Audio from the app's AudioUnit travels with the mirrored session. Quality/latency will be mirroring-grade, not "AirPlay video" grade, and the app cannot opt out (even `allowsExternalPlayback=false` doesn't stop it, per SO #45450460).
- (c) Control Center's audio-only route selection (long-press audio card) will route the app's `.playback` audio to an AirPlay receiver while video stays on-device — same as the in-app picker does for this app.

### Gaps
- No Apple page retrieved that documents mirroring's capture semantics for third-party rendered UIViews in technical terms (frame rate, resolution negotiation); the "mirroring captures whatever is on screen" claim is from Apple's WWDC phrasing ("share pretty much anything from your iOS screen") plus practitioner reports.

## Q6: What changed in iOS 17, 18, 19 and iOS 26 regarding AirPlay video for third-party apps?

### Takeaway
Nothing found that opens AirPlay video to non-AVPlayer pipelines. The documented deltas in the relevant window are: AVRouting's custom-protocol picker entries (iOS 16, pre-window but foundational); CarPlay gaining AirPlay *video streaming to the car display* in iOS 26 (receiver-side change, parked-only); and the next-generation AVSystemRouting/MediaDevice extension architecture announced for iOS/iPadOS 27. No iOS 17/18/19/26 release note, WWDC session, or documentation change located that adds a decoded-video-to-AirPlay API.

### Cited findings

- iOS 26 CarPlay: "iOS 26 introduces AirPlay video streaming support for both standard CarPlay and the CarPlay [Ultra]" — i.e. the car becomes an AirPlay *video receiver*; this is about a new receiver class, not a new sender API. — [CarPlay Hacks blog, iOS 26 feature list, updated for 26.5](https://blog.carplayhacks.com/ios-26-apple-carplay/) (2026; third-party blog, corroborated by [jasondeegan.com](https://jasondeegan.com/airplay-hits-carplay-in-ios-26-everything-you-need-to-know/) and [Tom's Guide](https://www.tomsguide.com/vehicle-tech/carplay-in-ios-26-5-biggest-upgrades-coming-to-your-car) — all secondary sources; treat as reported, not Apple-documented)
- AVSystemRouting / Media Device extensions: iOS/iPadOS 27.0+, "reviewed September 8, 2026" per the documentation mirror — URL-launch-based routing to third-party protocol receivers (see Q4 sources).
- WWDC19/501 and /507 remain the most recent Apple *sessions* devoted to third-party AirPlay video integration that I could find; both are AVPlayer/HLS-centric. — [WWDC19/501](https://developer.apple.com/videos/play/wwdc2019/501/), [WWDC19/507](https://developer.apple.com/videos/play/wwdc2019/507/) (June 2019)

### Inferences
- (c) Apple's investment is going into *routing/discovery* breadth (AVRouting → AVSystemRouting, more receiver classes) while the *sender-side video contract* stays AVPlayer + URL asset. There is no signal in 2023–2026 sources that a frame-upload AirPlay video API is coming.

### Gaps
- I did not find a consolidated Apple "What's new in AirPlay" for iOS 17/18/19; absence-of-evidence here means "no change found", not "no change exists". WWDC 2023–2025 session lists were not exhaustively searched.
- iOS 26 CarPlay AirPlay-video detail is from secondary sources only.

## Concrete-case synthesis (libVLC / VLCKit 4 IPTV app)

### Takeaway
For the described app, in-app AirPlay *video* is impossible without AVPlayer, on both documented and developer-reported evidence. Two escape hatches exist, each with a serious caveat: (1) libVLC's own renderer API (VLCRendererItem / libvlc_renderer) can discover AirPlay receivers and hand off the *stream URL* — but that makes the receiver fetch the IPTV stream itself, which a device-locked IPTV subscription forbids; (2) Control Center Screen Mirroring carries the libVLC-rendered UIView as-is, at mirroring quality. Audio-only AirPlay via the existing AVAudioSession works today with zero changes.

### Cited findings
- VLCKit exposes libVLC's renderer-discovery API: `VLCRendererItem.h` exists in the VLCKit 4 public headers (renderer items represent discovered render targets such as Chromecast/AirPlay devices in libVLC). — [VLCKit repository, Headers/Public/VLCRendererItem.h](https://code.videolan.org/videolan/VLCKit/-/blob/bf141df7e833681f89a2c5e40088be28bd389868/Headers/Public/VLCRendererItem.h) (code.videolan.org is behind an Anubis bot-check; the header's existence is confirmed via search index, content not directly retrieved — see Gaps)
- VideoLAN's stated design for VLCKit 4 AirPlay: "Support for AirPlay will be available in libvlc and VLCKit 4.0… It will allow you play anything from any source on Apple TV and if needed, will convert the media on-the-fly. Thus, AirPlay support will match what's possible with Chromecast right now. With VLCKit 3, there is no good way to do it." — [Stack Overflow #52473769, answer by VideoLAN-linked contributor](https://stackoverflow.com/questions/52473769/do-mobilevlckit-support-airplay-option-in-ios) (2018; old, and the page 504'd on direct fetch — snippet only; treat as a historical statement of intent, not current verified capability)
- The hand-off model caveat: "Chromecast, AirPlay etc. take a complete media source & just stream it themselves." — [media-kit issue #207, alexmercerind](https://github.com/media-kit/media-kit/issues/207) (July 1, 2023)

### Inferences
- (c) "Convert the media on-the-fly" in the VLC statement implies libVLC can *transcode and serve* the stream to the receiver from the device (as it does for Chromecast), which would bypass the receiver-fetches-URL problem — but this is libVLC's own AirPlay *sender* implementation (reverse-engineered protocol), not an Apple API, and its current reliability/legality-of-DRM-status on iOS is unverified by any 2023+ source I found.
- (c) Practical recommendation for the report writer: ship audio-only AirPlay (AVAudioSession already qualifies; optionally add AVRoutePickerView for UX), document Screen Mirroring as the video path, and evaluate VLCKit 4's VLCRendererItem AirPlay targets experimentally against the device-locked-stream constraint.

### Gaps
- Current (2024–2026) field reports of VLCKit 4's AirPlay renderer actually working on iOS for live MPEG-TS were not found; VideoLAN's gitlab is bot-protected and the 2018 statement is stale.
- Whether libVLC's on-the-fly conversion works when the source itself is bound to the device's network identity (it should, since libVLC re-serves from the device) is inference, not verified.
