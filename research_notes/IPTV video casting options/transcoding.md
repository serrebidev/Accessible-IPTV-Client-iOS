# On-device remux and transcode for IPTV video casting

Researched 2026-10-15. Latest steering: conversion must run on iPhone/iPad; private server is not the chosen solution. Source and shipped binary inspection completed on Windows; no Apple hardware execution.

## Can existing VLCKit 4.0.0-a22 produce compatible HLS without another media dependency?

### Takeaway
Yes at the source and shipped iOS binary level: a22 includes the modern VLC 4 HLS stream-output module, H264 VideoToolbox encoding, AAC encoding, transcode, TS mux and HTTP/file output. The least new code path is one existing VLCKit pipeline producing H264/AAC HLS on the iPhone, an app HTTP server serving that output, AVPlayer for AirPlay, and a VLC renderer consumer for Chromecast. This is an implementation candidate, not a hardware-proven guarantee.

### Cited Findings
- Exact a22 package points to `VLCKit-4.0-20260720-1538.zip` and checksum `d9de86d0c755cbcf46c49513ff57fffcd98258f0c7dd29f3e2d23bff3860da2a`. Package compile script pins libVLC `c9628afc4`. — [Package manifest](https://github.com/videolan/vlckit/blob/4.0.0-a22/Package.swift); [build script](https://github.com/videolan/vlckit/blob/4.0.0-a22/compileAndBuildVLCKit.sh)
- Independently downloaded the ZIP central directory plus compressed `VLCKit.xcframework/ios-arm64/VLCKit.framework/VLCKit` entry using HTTP ranges. Uncompressed binary is 49,777,832 bytes; SHA256 `127fbe4fc07f77c7d45ee6816f66dd9a6c88c60d50e0e340acaab2654fa740e5`. Actual binary string/symbol table contains `_vlc_entry__stream_out_hls_hls`, `_vlc_entry__stream_out_transcode_transcode`, `_vlc_entry__codec_videotoolbox_libvideotoolbox_enc`, `_vlc_entry__codec_avcodec_libavcodec`, `_vlc_entry__mux_mpeg_libmux_ts`, `_vlc_entry__access_output_http`, `_vlc_entry__access_output_file`, `_vlc_entry__stream_out_duplicate`, `_vlc_entry__stream_out_display`, and both Chromecast sout/demux entries. Also contains `AAC encoder`, `h264_videotoolbox`, and `venc=avcodec{codec=h264_videotoolbox,options{realtime=1}}`. These observations establish packaging, not successful execution. — [Exact inspected binary archive](https://download.videolan.org/cocoapods/unstable/VLCKit-4.0-20260720-1538.zip)
- Apple build disables sout/Chromecast only for watchOS. Global removal list removes old `access_output_livehttp`; **this does not remove modern `stream_out/hls`**. Prior findings that iOS cannot output HLS because livehttp is stripped are incomplete for a22. — [Pinned Apple build configuration](https://github.com/videolan/vlc/blob/c9628afc4/extras/package/apple/build.conf)
- Native VLC VideoToolbox encoder accepts H264 only, priority 1000, and sets AllowFrameReordering false. It does not configure target bitrate, profile, level or GOP; force FFmpeg's `h264_videotoolbox` through avcodec for more control. — [Native encoder](https://github.com/videolan/vlc/blob/c9628afc4/modules/codec/videotoolbox/encoder.c)
- `venc=avcodec{codec=h264_videotoolbox,keyint=60,bframes=0,options{realtime=1}}` is a source-supported candidate: avcodec selects explicit encoder name with `avcodec_find_encoder_by_name`, module `keyint` sets `AVCodecContext.gop_size`, and output bitrate sets `bit_rate`. Private FFmpeg options are fed to `avcodec_open2`; exact profile/level spellings and acceptance still need runtime validation. `aenc=avcodec{codec=aac,aac-profile=low}` selects AAC-LC. — [Encoder implementation](https://github.com/videolan/vlc/blob/c9628afc4/modules/codec/avcodec/encoder.c); [Chromecast's own avcodec options use](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/chromecast/cast.cpp)
- `maxwidth`, `maxheight`, `fps`, `vb`, `ab`, `channels`, `samplerate`, `deinterlace`, and `soverlay` are parsed transcode options. Max dimensions preserve the engine's sizing logic; fixed width and height risk distortion. — [Transcode module](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/transcode/transcode.c)
- Non-watchOS contributes FFmpeg encoding by default: `BUILD_ENCODERS=1` unless `--disable-sout`; `--disable-gpl` excludes x264 but native VideoToolbox avoids requiring x264. — [Contrib bootstrap](https://github.com/videolan/vlc/blob/c9628afc4/contrib/bootstrap); [FFmpeg rules](https://github.com/videolan/vlc/blob/c9628afc4/contrib/src/ffmpeg/rules.mak); [x264 rules](https://github.com/videolan/vlc/blob/c9628afc4/contrib/src/x264/rules.mak)

### Inferences
- Candidate full chain (replace track IDs and paths; untested on device):

```text
#transcode{vcodec=h264,venc=avcodec{codec=h264_videotoolbox,keyint=60,bframes=0,options{realtime=1}},fps=30,vb=4000,maxwidth=1280,maxheight=720,acodec=mp4a,aenc=avcodec{codec=aac,aac-profile=low},ab=128,channels=2,samplerate=48000,deinterlace,soverlay}:hls{variants="{ACTUAL_VIDEO_TRACK_ID,ACTUAL_AUDIO_TRACK_ID}",seg-type=ts,out-dir="/CACHE/SESSION",base-url="http://LAN_IP:PORT/TOKEN",num-seg=6,seg-len=2,pace=true}
```

- No extra FFmpeg binary dependency or homemade MPEG-TS segmenter is needed if this shipped module functions as its source describes. Parent implementation is using app `NWListener` serving session output with token path and CORS.
- “All decodable IPTV formats” means decode whatever this exact VLC build can decode, normalize into receiver-supported H264/AAC. It cannot promise every codec, DRM, damaged stream or real-time conversion of arbitrarily expensive inputs. Software decode still uses CPU even with hardware encoding.
- Pipeline alone routes output away from local display. Consume generated HLS with AVPlayer for local/AirPlay playback. Adding duplicate display consumes more resources and is unnecessary for this chosen arrangement. — [VLC duplicate module](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/duplicate.c)

### Gaps
- No iPhone/iPad execution of this exact chain, no empirical CPU/thermal/latency measurements, no receiver tests. Binary presence cannot certify decoding, encoder creation, HLS validity or AirPlay handoff.
- Background GPU restrictions exist; neither an audio background mode nor a route picker proves unrestricted hardware conversion while locked. Validate foreground, screen lock, background, interruption and thermal throttling separately. — [Apple background GPU guidance](https://developer.apple.com/documentation/metal/preparing-your-metal-app-to-run-in-the-background)

## What exact HLS integration details and traps must implementation handle?

### Takeaway
Use real VLC player string track IDs, start the relay only after closing the original provider connection, and serve generated HLS defensively. a22's modern HLS module has several source-visible shortcomings the HTTP layer must handle.

### Cited Findings
- HLS options: `variants` mandatory; `seg-type` `ts` (default) or `fmp4`; `base-url`; `host-http` default false; `max-memory` default 20000 KB; `num-seg` default 0; `out-dir`; `pace` default false; `seg-len` default 4, range 1–60 seconds. TS path uses `ts{use-key-frames}`; fmp4 uses `mp4frag`. — [Pinned HLS module](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/hls.c)
- Variant syntax is `{es_string_id,es_string_id},{another_id}`. Parser permits alphanumeric and `/` only, ignores whitespace, and matches IDs with exact `strcmp`. Nonmatching audio/video streams become EXT-X-MEDIA playlists. Master EXT-X-STREAM-INF entries derive only from matching variants; a fake/nonmatching variant does not create a playable normal master. — [Variant parser](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/variant_maps.c); [HLS Add and GenerateMainManifest](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/hls.c)
- `VLCMediaPlayer.Track` exposes string `trackId` and stable-ID metadata, while `VLCMedia.Track.identifier` is integer. Player `.videoTracks`/`.audioTracks` return player tracks. Use those string IDs, never assume `video/0` or numeric identifiers across providers. — [Track API](https://github.com/videolan/vlckit/blob/4.0.0-a22/Headers/Public/Media/VLCMedia.h); [Player track arrays](https://github.com/videolan/vlckit/blob/4.0.0-a22/Headers/Public/Playback/VLCMediaPlayer.h)
- Transcode stores original `es_id`, then audio/video paths forward it unchanged to downstream. `setid` changes only integer format ID, not the string ID HLS matches. — [Transcode Add/downstream](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/transcode/transcode.c); [Video downstream](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/transcode/video.c); [Audio downstream](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/transcode/audio.c); [setid](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/setid.c)
- Disk master file is `index.m3u8`; media manifests `playlist-N-manifest.m3u8`; segments `playlist-N-SEQUENCE.ts` (or fmp4 suffix); init file `playlist-N-init.mp4`. URL builder adds `/`, so base URL should have no trailing slash. — [HLS filenames](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/hls.c); [Segment naming](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/segments.c)
- Built-in `host-http=true` creates a VLC HTTP server via `vlc_http_HostNew`. It can store segments in memory without out-dir, but master HTTP endpoint is `base-url/stream.m3u8`, different from disk `index.m3u8`. Callback sets Content-Type and no-cache but does not implement CORS or token validation itself. — [InitHTTP and HTTPCallback](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/hls.c)
- `num-seg` bounds segment queue, but file storage destroy only frees allocated path; it does not unlink segment files. Disk usage therefore needs app cleanup. File writes use O_TRUNC, not atomic temp-and-rename. — [Segment eviction](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/segments.c); [File storage](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/storage.c)
- Source sets `will_destroy_segments = max_segments == 0`, then writes PLAYLIST-TYPE:EVENT when `!will_destroy_segments`, causing bounded sliding windows to be advertised as EVENT. This is reversed relative to queue behavior; app can remove that tag when serving live. Targetduration is configured seg-len, so verify actual segment durations/keyframe intervals satisfy HLS rules. — [GeneratePlaylistManifest](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/hls.c)
- Cast supported codecs/resolutions vary by receiver; H264/AAC in HLS provides a conservative common denominator, and proper CORS is needed for Cast web receiver media loading. — [Google Cast media support](https://developers.google.com/cast/docs/media)
- FFmpeg protocol layer supports user_agent, referer, headers, cookies and reconnect settings, but when reusing VLC input retain the project's VLC request handling rather than assuming bare URL is sufficient. — [FFmpeg network options](https://ffmpeg.org/ffmpeg-protocols.html)

### Inferences
- Capture selected original player's trackId strings, verify parser character constraints and stable-ID flag, stop provider playback, then start relay from original source with same request headers/cookies/auth and new sout. Original and relay must not remain independently connected on one-connection subscriptions. Receiver and local AVPlayer then consume only app HLS.
- Serve only known generated files from current session directory; opaque token path; GET/HEAD/OPTIONS and required CORS; correct media types; no provider credentials in receiver URL. Loopback is insufficient for receiver fetches; advertise active LAN address.
- Read manifests only after complete parseable contents, preserve last complete cached copy during O_TRUNC rewrite, strip wrong live EVENT tag, require usable video/audio playlist segments before AVPlayer handoff. Retry startup timeout and announce a clear error.
- Periodically prune segments absent from all current media manifests with a grace window for in-flight receiver requests, and delete the session directory after producer/server stop. `num-seg` alone is not disk cleanup.
- TS preferable initially: lower format complexity and established receiver support. Do not switch to fmp4 solely because it sounds newer; validate generated CMAF on target receivers first.

### Gaps
- No runtime validation that original and restarted stream expose same track strings for every demux/provider. Public stability property matters; some tracks may be unstable.
- No runtime validation that nested options `profile=main,level=3.1` are accepted in the shipped FFmpeg h264_videotoolbox encoder. `keyint`/`bframes` are explicit VLC avcodec keys and are source verified. Avoid claiming tested bitrate/level bounds.

## What alternatives were examined, and why not add one now?

### Takeaway
The strongest maintained command/session dependency is original-author FFmpegKitNext, but it is source-only and needs a separate reproducible macOS build. Existing a22 HLS/transcode functionality is a smaller first implementation. Server conversion remains an alternative architecture but was explicitly excluded by the user's latest choice.

### Cited Findings
- GitHub discovery was run with `gh search repos 'ffmpeg-kit in:name' --sort updated` and `--sort stars`. Relevant high-star results: original arthenica/ffmpeg-kit 5851; kingslay/FFmpegKit 229; arthenica/ffmpeg-kit-next 163; ffmpeg-kit-extended 67; tylerjonesio/ffmpeg-kit-spm 38 at inspection. Updated-sort includes fresh zero-star wrappers; recency alone did not establish viability. — [GitHub repository search](https://github.com/search?q=ffmpeg-kit+in%3Aname&type=repositories&s=stars&o=desc)
- Old FFmpegKit is retired, **but original author resumed development as FFmpegKitNext in July 2026**. Current Next latest tag v9.0.0 published 2026-08-23; release has no binaries/assets. — [Original notice](https://github.com/arthenica/ffmpeg-kit); [Next releases](https://github.com/arthenica/ffmpeg-kit-next/releases)
- FFmpegKitNext explicitly supports iOS/iPadOS 12.1+, tvOS 11+, visionOS 1+, Objective-C APIs and local shared frameworks/XCFramework/SPM generation. It exposes execute/executeAsync, argument-array variants, session callbacks/logs/statistics and session cancellation; no custom demux/mux pipeline required. Example builds `./nix-ios.sh -p xcode26 -x --spm`, corresponding tvOS/visionOS wrappers, then `nix-apple.sh` umbrella. Xcode 26 required by current docs. No prebuilt binaries. — [Apple integration and API](https://github.com/arthenica/ffmpeg-kit-next/blob/main/apple/README.md); [FFmpegKit.h](https://github.com/arthenica/ffmpeg-kit-next/blob/main/apple/src/FFmpegKit.h)
- FFmpegKitNext is LGPL3 by default, GPL3 when GPL libraries enabled. Shared dynamic framework integration and source/license distribution obligations remain; avoid adding x264/GPL when VideoToolbox suffices. — [Next licensing](https://github.com/arthenica/ffmpeg-kit-next#14-license); [FFmpeg compliance guidance](https://ffmpeg.org/legal.html)
- Public kingslay/FFmpegKit is GPL3; its public wrapper source `ffmpegkit.c` contains only `dummy(void)` and C library shims. Paid LGPL version advertises running ffmpeg/ffprobe; public package should not be mistaken for arthenica's command/session API. All Apple platforms advertised. — [Repository README](https://github.com/kingslay/FFmpegKit); [Actual wrapper source](https://github.com/kingslay/FFmpegKit/blob/main/Sources/FFmpegKit/ffmpegkit.c); [SPM manifest](https://github.com/kingslay/FFmpegKit/blob/main/Package.swift)
- KSPlayer public package now defaults GPL with paid LGPL offering. Public framework is binary-only for macOS/simulator/tvOS; source for all Apple platforms is in paid variant. It advertises conversion but no inspected turnkey all-format live HLS caster. A replacement player would expand scope and impose licensing/API work. — [Current KSPlayer README](https://github.com/kingslay/KSPlayer)
- tylerjonesio/ffmpeg-kit-spm explicitly retired; latest binary release v5.1.2 dated 2023-01-14; iOS/macOS/tvOS only, no visionOS advertised. Not a maintained dependency choice. — [Retirement README](https://github.com/tylerjonesio/ffmpeg-kit-spm); [Release](https://github.com/tylerjonesio/ffmpeg-kit-spm/releases/tag/v5.1.2)
- ffmpeg-kit-extended currently supports iOS and tvOS native/RN, not Flutter tvOS, and advertises LGPL/GPL builds and FFmpeg 9.0.1. VisionOS not in inspected supported platform table. Primarily Flutter/RN integration, so not the smallest native Swift choice here. — [Current README](https://github.com/akashskypatel/ffmpeg-kit-extended)
- Jellyfin distinguishes remux/direct stream (container/audio conversion) and video transcode, supports hardware acceleration, and can serve compatible HLS; it requires a running server and client integration. — [Codec support](https://jellyfin.org/docs/general/clients/codec-support/); [Hardware acceleration](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/)
- Dispatcharr v0.25 introduced named output profiles with on-the-fly FFmpeg transcoding, shared transcode process for clients requesting same profile, and fMP4/TS output. Those features are not proof of a native HLS endpoint for live channels. — [Official v0.25 release](https://github.com/Dispatcharr/Dispatcharr/releases/tag/v0.25.0)
- Threadfin is M3U proxy middleware using FFmpeg/VLC buffers; not a documented standalone turnkey HLS cast-transcode API found in this inspection. — [Threadfin repository](https://github.com/Threadfin/Threadfin)

### Inferences
- If existing VLC HLS fails real device testing, build a pinned LGPL FFmpegKitNext XCFramework once in a dedicated dependency workflow, publish immutable checksummed artifacts, reuse in app CI. Do not compile all codecs/platform slices from scratch during every app release.
- An embedded FFmpeg HLS command plus local HTTP server is valid fallback architecture. FFmpeg supports native HLS muxing, segment lists, atomic temp files and delete_segments. — [HLS muxer documentation](https://ffmpeg.org/ffmpeg-formats.html#hls-2)
- A server would reduce phone thermal/background pressure but adds account setup, network reachability and credential handling. The selected on-device requirement rules out presenting that as the complete answer.

### Gaps
- No measured macOS build duration for FFmpegKitNext; a fresh three-platform build fitting a 90-minute app CI budget is **not established**. Repository exposed web/Android automation but no inspected successful timed Apple artifact build. Treat separate build/cache as necessary preparation, not an estimate.
- MoonPlayer did not yield a verified reusable Swift live HLS conversion API; no recommendation based on branding or generic FFmpeg playback support.
- Distribution licensing assessment is technical scoping, not legal certification. Current repo MIT code and LGPL dependencies can coexist with compliance; GPL public KSPlayer/kingslay artifacts alter the redistribution obligations of a combined distribution.
