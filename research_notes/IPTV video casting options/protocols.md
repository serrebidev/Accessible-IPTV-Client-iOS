# Apple AirPlay and Google Cast video protocols

Research checked 2026-10-15. Official Apple/Google sources; statements labelled inference are engineering conclusions, not vendor promises. Existing VLCKit and one-connection/provider constraints come from coordinator assignment, not independently verified here.

## Which APIs provide actual video routes, and on which platforms?

### Takeaway

For iPhone/iPad, use AVPlayer external playback plus AVRoutePickerView for AirPlay, and Google's Cast iOS SDK for Chromecast video. Native tvOS/visionOS sender support must be treated separately; the existence of a shared SwiftUI target or an audio route does not establish video casting support. [Apple AirPlay](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app), [Google architecture](https://developers.google.com/cast/docs/overview)

### Cited Findings

- Apple recommends adding AVRoutePickerView and identifies AVPlayer/AVQueuePlayer as its simple buffered playback APIs suitable for video. AVSampleBufferAudioRenderer is the flexible *audio* path; that documentation does not offer an arbitrary decoded-video-buffer AirPlay sender. [Supporting AirPlay](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app)
- AVRoutePickerView presents nearby media receivers; `prioritizesVideoDevices = true` orders video devices first. Apple supplies an actual SwiftUI `UIViewRepresentable` example. The current documentation metadata lists iOS/iPadOS 11+, tvOS 11+, macOS and Catalyst; **visionOS is absent**. [AVRoutePickerView](https://developer.apple.com/documentation/avkit/avroutepickerview), [Apple machine-readable metadata inspected](https://developer.apple.com/tutorials/data/documentation/avkit/avroutepickerview.json)
- `AVPlayer.allowsExternalPlayback` permits external playback and defaults to true; `isExternalPlaybackActive` indicates that video is actually playing externally. Both current metadata sets list iOS/iPadOS 6+ and tvOS 9+, with no visionOS entry. [allowsExternalPlayback](https://developer.apple.com/documentation/avfoundation/avplayer/allowsexternalplayback), [isExternalPlaybackActive](https://developer.apple.com/documentation/avfoundation/avplayer/isexternalplaybackactive)
- Apple's Vision Pro support documents system “Mirror My View,” up to 1080p, plus a separate audio routing area. Protected purchased video blacks out while mirroring. This documents system mirroring, not an in-app AVPlayer external-video sender API. [Apple Vision Pro mirroring](https://support.apple.com/en-gb/119944)
- Google documents iOS, Android and web sender platforms. Its current official SPM package declares only `.iOS(.v16)`; the native package does not advertise tvOS or visionOS. Do not present an iOS-compatibility app running on Vision Pro as a verified native visionOS integration. [Google sender platforms](https://developers.google.com/cast/docs/reference), [official Package.swift](https://github.com/googlecast/google-cast-ios-sdk/blob/main/Package.swift)
- The official setup body, updated 2026-10-13, says iOS 16+, SDK 4.8.6, SPM recommended. Its autogenerated summary still says iOS 15; the package agrees with the body. Discovery needs `NSBonjourServices` entries `_googlecast._tcp` and `_<APPID>._googlecast._tcp`, plus `NSLocalNetworkUsageDescription`. [Google setup](https://developers.google.com/cast/docs/ios_sender)
- Actual Cast lifecycle: initialize `GCKCastContext` with a receiver ID, use `GCKUICastButton`/discovery, get `GCKCastSession.remoteMediaClient`, build `GCKMediaInformation` from a **content URL**, MIME type and live/buffered stream type, then load. SDK operations run on the main thread. [iOS integration](https://developers.google.com/cast/docs/ios_sender/integrate)
- Prefer the modern `GCKMediaLoadRequestDataBuilder` → `loadMediaWithLoadRequestData:` API; the reference recommends it over older `loadMedia:` overloads. [RemoteMediaClient reference](https://developers.google.com/cast/docs/reference/ios/interface_g_c_k_remote_media_client)
- Default Media Receiver needs no custom receiver application. Authentication/custom JavaScript and other special capabilities call for a registered Custom Receiver. A custom receiver is a web app hosted by the developer; its published hosting must support TLS. [Receiver choice](https://developers.google.com/cast/docs/overview), [Custom Receiver](https://developers.google.com/cast/docs/web_receiver/basic)

### Inferences

- Keep VLCKit for local playback. A route picker alone does not convert its decoded video into AVPlayer external playback. Build a separate compatible video source for AVPlayer and Cast rather than treating an audio-route change as proof. This follows the distinct Apple video/audio paths and Cast URL loading model. [Apple playback paths](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app), [Cast load model](https://developers.google.com/cast/docs/ios_sender/integrate)
- Compile GoogleCast into the iOS target only unless Google ships explicit native slices/support for other platforms. Keep visionOS and tvOS feature labels honest: documented native API presence on tvOS still needs real receiver testing; native visionOS AVPlayer external video is not established here. [Google package](https://github.com/googlecast/google-cast-ios-sdk/blob/main/Package.swift), [Apple availability](https://developer.apple.com/tutorials/data/documentation/avfoundation/avplayer/allowsexternalplayback.json)

### Gaps

- No macOS build or device testing was performed. Exact tvOS sender video behavior and native visionOS alternatives require an SDK compile plus hardware validation. No official native GoogleCast tvOS/visionOS support claim was found in the reviewed docs/package.

## Which IPTV inputs can work directly, and what conversion is actually available?

### Takeaway

Use HLS as the shared delivery format and H.264/AAC as the conservative compatibility output. Remux compatible compressed streams; transcode unsupported codecs. MPEG-TS container support does **not** establish that every endless IPTV `.ts` endpoint can be cast directly, and the docs do not justify saying every `.ts` endpoint is impossible either. [Apple HLS specification](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html), [Cast media](https://developers.google.com/cast/docs/media)

### Cited Findings

- Apple HLS permits H.264 in TS or fragmented MP4, requires HEVC in fMP4, and recommends H.264 variants at or below High Profile Level 4.1 for maximum compatibility. The specification targets iOS, tvOS, macOS and visionOS, but receiver/model capabilities still matter. [Apple HLS authoring specification](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html)
- Google lists **MP2T** among supported media containers, so a blanket “Chromecast cannot accept TS” is incorrect. It explicitly says **HEVC in Transport Stream is unsupported**. First/second-generation Chromecast H.264 limit is High Profile Level 4.1, up to 1080p30 or 720p60; later models differ. Receiver-side `CastReceiverContext.canDisplayType()` checks codec/device capability. [Supported Media for Google Cast](https://developers.google.com/cast/docs/media)
- The CAF Web Receiver documented adaptive protocols are DASH, HLS and Smooth Streaming. HLS uses master/media playlists and segments. Google documents HLS codecs via CODECS, with H.264/AAC defaults if omitted; explicit codec descriptions avoid guessing. [Web Receiver Streaming Protocols](https://developers.google.com/cast/docs/media/streaming_protocols)
- Apple's `AVAssetWriter` can emit HLS/CMAF fMP4 initialization/media segment data through its delegate. Set `outputFileTypeProfile` to `.mpeg4AppleHLS`, set segment interval/start time, append sample buffers. `outputSettings: nil` passes compressed samples through; configured compression settings encode. **The app writes the playlist** and provides hosting. Normal passthrough segmentation only accepts one input, so separate audio/video writers with a master playlist are one documented arrangement; custom segmentation can mux with extra alignment responsibility. [Apple WWDC20 session and code](https://developer.apple.com/videos/play/wwdc2020/10011/)
- Apple's VideoToolbox exposes hardware encoder/decoder sessions and explicitly covers live-stream encoding. Capabilities vary by device; inspect available codec/properties rather than promising a universal hardware codec. [VideoToolbox](https://developer.apple.com/documentation/videotoolbox)
- Apple describes preparing media for AirPlay as requiring Apple-playable media and HTTP delivery, including appropriate MIME types for playlists, TS segments and MP4. This is an old archive and its old codec/profile guidance should not replace the current HLS specification. [AirPlay media/server preparation](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AirPlayGuide/PreparingYourMediaforAirPlay/PreparingYourMediaforAirPlay.html)

### Inferences

- For a provider's live TS endpoint that fails when renamed to `.m3u8`, fetch the original URL unchanged and **generate a new local HLS playlist/segments**. A filename rewrite cannot perform segmentation or demuxing. Compatible H.264/AAC TS may allow stream-copy segmentation; HEVC TS requires fMP4 packaging for compatible receivers; MPEG-2 video or unsuitable audio may need transcoding. These conclusions follow format requirements, not a claim that Apple supplies a ready-made IPTV demuxer. [Apple HLS requirements](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html), [Apple writer inputs](https://developer.apple.com/videos/play/wwdc2020/10011/), [Google HEVC restriction](https://developers.google.com/cast/docs/media)
- One source connection feeding one gateway, with local playback and the TV consuming that gateway, best preserves a one-connection subscription. Direct receiver loading should first stop local provider playback and probing; even then no vendor doc guarantees a provider releases its slot immediately. This is an architectural recommendation based on receiver URL loading. [Cast loading](https://developers.google.com/cast/docs/ios_sender/integrate)
- Native AVAssetWriter/VideoToolbox are supported pieces of a conversion path, not an off-the-shelf replacement for libavformat or VLCKit's parser. The missing bridge is provider demuxing/decoding into correctly timed sample buffers. A custom receiver cannot simply add a missing hardware decoder; it can customize URL/auth/protocol handling while remaining subject to device media support. [Apple authoring pipeline](https://developer.apple.com/videos/play/wwdc2020/10011/), [Google receiver codec checks](https://developers.google.com/cast/docs/media)

### Gaps

- No official documentation found here guarantees arbitrary endless raw HTTP TS support on every Cast model; this needs representative-device testing. No VLCKit a22 demux/sample extraction APIs were examined in this subtask. Phone-local conversion throughput, thermal behavior, interlace handling and licensing/build feasibility remain implementation research.

## What networking, authentication and background limits constrain a phone gateway?

### Takeaway

A foreground iPhone can host a gateway using native networking APIs, but reliable locked-phone transcoding/HTTP serving is a separate acceptance condition. Direct receiver playback avoids continuous phone conversion work when URLs, authorization and codecs permit it. [NWListener](https://developer.apple.com/documentation/network/nwlistener), [Apple background execution](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time), [Google lifecycle](https://developers.google.com/cast/docs/ios_sender/integrate)

### Cited Findings

- `NWListener` accepts incoming network connections and is available iOS/tvOS 12+ and visionOS 1+. It is a connection primitive, **not a ready-made HTTP or HLS server**. [NWListener](https://developer.apple.com/documentation/network/nwlistener), [availability metadata](https://developer.apple.com/tutorials/data/documentation/network/nwlistener.json)
- CAF loads adaptive content through browser requests and enforces CORS. Content that plays on iOS may therefore fail on Cast. [Custom Receiver CORS](https://developers.google.com/cast/docs/web_receiver/basic)
- Custom Receiver `PlaybackConfig` has outgoing manifest request handlers and credentials configuration; the docs show `withCredentials = true` for cookies/authorization. The receiver must receive and use its own authorization state; an iOS URLSession's headers are not automatically a Cast media transport. [Custom Receiver core features](https://developers.google.com/cast/docs/web_receiver/core_features)
- Apple's archived encrypted-HLS AirPlay guidance supports authenticated key delivery, HTTPS cookies and custom key loading. It warns that authentication may require interaction on the sending device and cookie/token lifetime must outlast playback. Thus “AirPlay cannot work with authentication” is false. [Apple AirPlay encryption and authentication](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AirPlayGuide/EncryptionandAuthentication/EncryptionandAuthentication.html)
- Apple staff explicitly states `AVURLAssetHTTPHeaderFieldsKey` is **not a supported API**. Do not build reliable casting around that undocumented dictionary key. [Apple staff response](https://developer.apple.com/forums/thread/671139)
- Apple says AirPlay video apps need audio background mode plus a playback-category AVAudioSession so video continues after leaving the app. This is an actual supported AirPlay playback case. [WWDC19 AirPlay 2](https://developer.apple.com/videos/play/wwdc2019/501/)
- General UIKit background extensions provide finite extra runtime; the app is ordinarily suspended shortly after background transition, and failing to end expiring tasks can cause termination. They are not an indefinite web-server entitlement. [Extending background execution time](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)
- Google suspends the sender's Cast session when its app backgrounds and attempts resumption on return. Cast session control lifecycle and receiver playback/data-fetch lifecycle are distinct. [iOS Cast session lifecycle](https://developers.google.com/cast/docs/ios_sender/integrate)

### Inferences

- For Cast, give the receiver a LAN-reachable gateway address such as `http://<phone-LAN-IP>:<port>/<unguessable-session>/master.m3u8`; loopback points to the receiver itself. Rewrite all child playlist/segment/key URLs that must stay proxied, implement required CORS, correct MIME, range handling where needed and a bounded live segment window. Validate Wi-Fi isolation, VPN routing, network changes and receiver HTTP policy. This is networking design inferred from the documented receiver fetching/CORS model, not a vendor guarantee of arbitrary LAN HTTP. [Receiver data fetching](https://developers.google.com/cast/docs/web_receiver/basic), [streaming structure](https://developers.google.com/cast/docs/media/streaming_protocols)
- For AirPlay, do not assume all receiver types pull every original URL themselves, or that all require a public URL. Apple supports local and Internet media and authenticated key loading. A LAN-reachable HTTP source is the practical shared gateway design; verify receiver URL fetches, cookies and lock behavior on real devices rather than imposing unsupported blanket restrictions. [AirPlay scope](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AirPlayGuide/Introduction/Introduction.html), [authenticated delivery](https://developer.apple.com/library/archive/documentation/AudioVideo/Conceptual/AirPlayGuide/EncryptionandAuthentication/EncryptionandAuthentication.html)
- AirPlay background playback support does not by itself promise indefinite arbitrary demux/transcode work plus a LAN server while locked. Chromecast sender background suspension does not necessarily stop an already-independent receiver, but it can starve a phone-hosted gateway if the app loses runtime. Treat reliable lock/background operation as a hardware proof gate. A continuous server elsewhere is the practical fallback when that gate fails. [Apple supported playback case](https://developer.apple.com/videos/play/wwdc2019/501/), [general runtime](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time), [Cast session lifecycle](https://developers.google.com/cast/docs/ios_sender/integrate)
- Recommendation: first prove one-source TS→HLS remux and video on actual AirPlay and Cast receivers, then add transcode only for actual unsupported inputs. Test lock/background before promising broad support. Direct compatible URLs are an optimization, with provider handoff managed explicitly; the shared gateway is what preserves credentials, format conversion and one source connection. [Apple fMP4 pipeline](https://developer.apple.com/videos/play/wwdc2020/10011/), [Google formats](https://developers.google.com/cast/docs/media)

### Gaps

- No official guarantee located for indefinite iOS third-party LAN HTTP serving and hardware video transcoding solely because remote Cast video is playing. No measurements of this repo's background strategy, route authentication or physical receivers were performed. Do not turn this absence into “impossible”; make it a prototype and real-device acceptance test.
