# Convert IPTV Locally For Wireless Video

**Use the iPhone or iPad as the converter and media gateway, then send compatible video to AirPlay or Chromecast.** No separate computer, private server or cloud conversion service is required by this design; the app itself must serve the converted stream over the local network. No reviewed GitHub project supplies a verified, universal solution by itself. The smallest promising implementation reuses this app’s existing **VLCKit 4.0.0-a22**, whose shipped iOS binary contains HLS output, transcoding and hardware H.264 encoder modules. Native AVPlayer can consume that output for AirPlay video, while the existing VLC renderer path remains relevant for Chromecast. This is a source-backed implementation route, **not proof of reliable conversion on physical devices**. Source-built FFmpegKitNext is the fallback if VLCKit’s output cannot meet runtime requirements. ([VLCKit package](https://github.com/videolan/vlckit/blob/4.0.0-a22/Package.swift), [Apple AirPlay](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app), [FFmpegKitNext](https://github.com/arthenica/ffmpeg-kit-next))

**AetherEngine is the strongest recent architectural reference, not the complete answer.** It remuxes compatible video into HLS and uses AVPlayer, but its documented software-rendered video route provides audio-only AirPlay. Its video dependencies exclude video encoders, and current iOS/tvOS minimum versions are 18, above this app’s 17. KSPlayer and media-kit similarly do not turn every locally decoded format into castable video. HLSRemuxKit cannot repair an unsupported codec. SwiftCast actually sends video media URLs, but it does not transcode them. ([Aether formats](https://github.com/superuser404notfound/AetherEngine/blob/main/docs/formats.md), [Aether package](https://github.com/superuser404notfound/AetherEngine/blob/main/Package.swift), [FFmpegBuild](https://github.com/superuser404notfound/FFmpegBuild), [media-kit maintainer explanation](https://github.com/media-kit/media-kit/issues/721#issuecomment-1977223540))

Receiver projects such as UxPlay and AirAP operate in the opposite direction; audio projects such as Shairport Sync do not supply video sending. Their popularity cannot establish an iOS sender solution. ([UxPlay](https://github.com/FDH2/UxPlay), [AirAP](https://github.com/neon443/AirAP), [Shairport Sync](https://github.com/mikebrady/shairport-sync))

## One phone gateway can supply both video routes

The practical architecture is **one provider connection → demux/decode as needed → compatible HLS → phone-hosted HTTP → receiver**. Keep the provider’s original `.ts` URL unchanged; create a new local playlist and segments. Renaming an upstream URL to `.m3u8` does not convert it. Compatible tracks can be remuxed; unsupported video needs encoding, interlaced video needs suitable processing, and unsupported audio needs conversion. **H.264 plus AAC in HLS** is the conservative shared target, with resolution, profile and frame rate selected for the receiving device. Google supports MP2T, so “Chromecast cannot play TS” is too broad; Google explicitly excludes HEVC in TS, and device codec limits differ. ([Apple HLS specification](https://developer.apple.com/streaming/hls-authoring-specification-for-apple-devices.html), [Google supported media](https://developers.google.com/cast/docs/media))

For **AirPlay video**, AVPlayer plays the generated compatible asset and the system route picker selects the receiver. On iOS the picker acts on the active playback session; its `player` binding is macOS-only. Routing libVLC’s audio does not upload its rendered picture. Observe actual external playback and report errors audibly. For **Chromecast video**, preserve the existing VLCKit renderer integration where it works; Google’s iOS Cast SDK can alternatively load the shared HLS URL. SwiftCast is a broader Apple-platform sender candidate, with substantially less published adoption. None supplies the missing conversion merely by selecting a receiver. ([Apple playback paths](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app), [Picker player availability](https://developer.apple.com/tutorials/data/documentation/avkit/avroutepickerview/player.json), [AVPlayer external state](https://developer.apple.com/documentation/avfoundation/avplayer/isexternalplaybackactive), [Cast integration](https://developers.google.com/cast/docs/ios_sender/integrate), [SwiftCast](https://github.com/CreatureSurvive/SwiftCast))

Use a LAN-reachable phone address and an unguessable session path. Keep provider credentials and required headers in the phone’s upstream client; serve only generated media to the TV. Provide correct playlists, MIME types, CORS where required, bounded segment retention and network-change handling. Stop the original provider player before starting the gateway, or make local playback consume its output, to avoid two continuing provider sessions. These are engineering requirements inferred from receiver fetching and HLS delivery, not a vendor guarantee for every network. ([Cast receiver fetching and CORS](https://developers.google.com/cast/docs/web_receiver/basic), [HLS streaming](https://developers.google.com/cast/docs/media/streaming_protocols))

## The shipped VLCKit binary deserves the first prototype

The pinned package downloads **VLCKit-4.0-20260720-1538.zip**. Inspection of its actual iOS arm64 Mach-O found `_vlc_entry__stream_out_hls_hls`, together with transcode, TS muxing, libavcodec and VideoToolbox encoding components. **Missing legacy `livehttp` does not mean HLS output is missing:** this is VLC’s newer HLS module. Module presence establishes shipped building blocks, not successful operation of the proposed chain. ([Pinned package](https://github.com/videolan/vlckit/blob/4.0.0-a22/Package.swift), [Exact binary archive](https://download.videolan.org/cocoapods/unstable/VLCKit-4.0-20260720-1538.zip))

The source-backed route configures media stream-output options before playback: transcode to H.264/AAC, then write rolling HLS using selected stream IDs in the required variant declaration. Use the public player track’s **string `trackId`**, not guessed `video/0` values or integer media-track identifiers. This avoids replacing the working player or importing another large codec stack first. Runtime proof must establish that this exact build accepts the options, preserves track identities after restart, produces playable segments and maintains timing. The pinned HLS source does not delete evicted disk segments, labels bounded sliding playlists as EVENT and rewrites manifests nonatomically; the app must compensate with cleanup and defensive serving. ([Track API](https://github.com/videolan/vlckit/blob/4.0.0-a22/Headers/Public/Media/VLCMedia.h), [Pinned HLS implementation](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/hls.c), [Disk storage](https://github.com/videolan/vlc/blob/c9628afc4/modules/stream_out/hls/storage.c))

If that prototype fails, **FFmpegKitNext is the strongest fallback**. It supports iOS/iPadOS, tvOS and visionOS and executes FFmpeg argument arrays asynchronously. It ships source rather than official prebuilt Apple binaries: build and package the needed XCFramework slices on macOS, enabling required platform encoders and retaining a controlled decoder set. Native AVAssetWriter/VideoToolbox are useful components, but adopting them directly still leaves provider demuxing, decoding, timestamps, playlists and hosting to implement. ([FFmpegKitNext Apple instructions](https://github.com/arthenica/ffmpeg-kit-next/tree/main/apple), [Execution API](https://github.com/arthenica/ffmpeg-kit-next/blob/main/apple/src/FFmpegKit.h), [Apple HLS segment writing](https://developer.apple.com/videos/play/wwdc2020/10011/))

## “All decodable formats” still requires device limits

The earlier blanket conclusion that in-app AirPlay video was impossible was **too broad**. The narrower supported finding is that a custom video display layer has no documented arbitrary-frame AirPlay upload API. Converting on the phone into an AVPlayer-compatible stream provides a legitimate video route. Missing evidence for that bridge was not evidence that it could not be built. ([Apple AirPlay](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app), [Apple HLS writing](https://developer.apple.com/videos/play/wwdc2020/10011/))

“All” must mean inputs the compiled decoder can actually decode and the phone can convert in real time; it cannot cover DRM without authorization, corrupt streams or unlimited resolution/thermal load. Verify MPEG-2/interlaced broadcasts and incompatible audio alongside common H.264 and HEVC inputs. Define handling for HDR, multiple tracks and subtitles explicitly. Background operation is another proof gate: supported AirPlay playback does not guarantee indefinite third-party transcoding plus HTTP serving while locked, and Cast sender suspension can starve a phone-hosted stream. With no external server allowed, any failed background gate becomes a clearly stated foreground-use limit. ([VideoToolbox](https://developer.apple.com/documentation/videotoolbox), [Apple background runtime](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time), [Cast lifecycle](https://developers.google.com/cast/docs/ios_sender/integrate))

Scope the first delivery to **iPhone/iPad sending**. Google’s official Swift package targets iOS; native tvOS/visionOS GoogleCast support is not established. Apple’s external-video API availability and receiver behavior also require platform-specific validation. Licensing remains part of packaging: FFmpegKitNext defaults to LGPL-3.0 and becomes GPL with GPL components; KSPlayer’s free distribution is GPL; HLSRemuxKit lacks a detected repository license. Reusing VLCKit avoids another dependency but does not remove existing license obligations. ([Google package](https://github.com/googlecast/google-cast-ios-sdk/blob/main/Package.swift), [Apple external playback](https://developer.apple.com/documentation/avfoundation/avplayer/allowsexternalplayback), [FFmpegKitNext license](https://github.com/arthenica/ffmpeg-kit-next), [KSPlayer license](https://github.com/kingslay/KSPlayer))

## Conclusion

The useful next decision is whether the **already shipped decoder and encoder stack can produce a stable shared output on actual hardware**. Prove AirPlay picture, Chromecast picture, incompatible-codec conversion, one upstream session and phone-lock behavior before expanding dependencies or claiming universal support. This research establishes a concrete on-device route; it does not claim a completed implementation, a successful macOS build, sustained thermal performance or receiver validation.
